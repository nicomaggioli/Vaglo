Technical details

The whole system, described honestly.

Most pages like this one leave out the parts that do not flatter them. Below is every substantial part of the system, including where the edges are and the things it refuses to do.

Everything below is shipped and in daily use

What's not on this page

Some of the system is built but not load-bearing yet, so I don't sell it as though it were. The proposal lifecycle analytics view still runs on sample data. 01 · Discovery

The nightly watch

A twenty-step pipeline runs unattended every night in three phases: sync and health, then deliverables, then a reviewed wrap-up. Each phase gates on the one before it, so a failed database restore or a bad code sync stops the run instead of producing a brief built on stale data.

It searches the federal opportunity API once per set-aside code, merges and de-duplicates by notice ID, filters to your NAICS codes, and downloads the complete package into a folder per opportunity: base solicitation, attachments, amendments, drawings.

The freshness re-check is the underrated part. Every night it re-verifies everything you're still tracking against the current listing: due dates that moved, notices withdrawn, notices quietly amended, new attachments posted. One wide search, diffed locally, so the API cost is fixed no matter how many opportunities you track.

It also spots notices where an agency has already chosen a winner, and buries them. It won't say so without two corroborating signals plus a named recipient.

02 · Comprehension

Reading the solicitation

One command turns the whole package into structured data: mixed PDF, Word, Excel and text, detected by content rather than file extension. First it sorts the solicitation into one of five types, because a design job, a construction management job, and a general construction job you shouldn't be bidding all need different handling.

Then it parses every document in parallel, merges the results with amendments taking precedence over the base document, and extracts a structured record: scope, required roles, evaluation factors and their weights, set-aside and size standards, key dates, page limits, submission mechanics, the contracting officer.

Then it stops and asks you. Before anything is built on that reading, it shows you its own understanding of the solicitation with the verbatim source sentence behind every line. Flag a line as wrong and it demands a written note. Add scope it missed.

No AI in that step, on purpose. An AI-rewritten summary would put back the exact risk the checkpoint exists to catch. Your sign-off is fingerprinted to that parse, so a re-analysis makes it go stale instead of quietly standing.

When the primary model fails, the run fails loudly. There's a working second provider, switched off by default, because a silent fallback turns a broken process into a quiet one.

03 · Judgement

Deciding what to chase

Three layers, and you can see all three.

1

The read

A base score out of 100 from the gap analysis: personnel coverage against required roles, past-performance match, location, certifications, scope alignment. It comes with a written rationale.

2

Your rules

Deterministic adjustments you author in plain English and edit from the dashboard. "Anything past the Mississippi: minus 15." Every adjustment shows the rule that produced it.

3

What it learned

A statistical model keeping separate posteriors per state, agency, fee band, set-aside and discipline, with credible intervals. It's exposed over an API so the score stays auditable.

The cold-start answer

The learned layer carries zero weight until enough decisions exist to justify influence, and earns its way up from there. It can't learn the wrong thing from your first ten calls, because for your first ten calls it isn't voting.

04 · Selection

Choosing the projects and the people

This is the real work of a qualifications submission, and it usually gets done from memory the week of the deadline.

The engine flips the usual order. It ranks your whole portfolio against this solicitation first, and eligibility is annotated rather than filtered, so a project that fails a cost threshold is marked and still on screen instead of quietly dropped. Then the team comes out of the winning slate, because the strongest qualification a person can carry is that they did that discipline themselves on a project you're already submitting.

The whole ranking path is deterministic. No AI call, no variance: the same inputs give the same slate, and every pick carries a printed reason.

Measured against a human

On a live solicitation I compared the recommender's slate against the team the firm's owner had built by hand. Nine of fifteen top picks matched exactly. In four of the six divergences the owner's pick was already sitting in the alternates, and all three subconsultant firms rolled up identically.

It also blocks two known-bad picks the old approach still surfaced, one of them a design that was never constructed reaching slot three of a submitted package.

05 · Production

The package

Twenty-nine generator modules and a set of base templates with every form field individually mapped. This is the part nothing else in the category does.

Résumés

One per person, per role. Written from your records, then the facts your database owns are written back over anything generated. Any project the draft names that isn't in that person's real history gets flagged.

Project sheets

Each chosen project rendered to the form's layout, with a constraint on relevance: only a real match may claim direct relevance, not a project that happens to share a discipline.

The matrix

Twenty people by ten projects is two hundred cells, and it's the section firms most often get wrong by hand. Built from relational joins with no AI at all.

The narrative

Eight to fifteen pages, reordered to mirror the agency's published evaluation factors, with more page budget for higher-weighted ones. A second pass checks every scored factor was answered.

Partner forms

A qualifications form for every teaming firm, prime included. One live package carried ten. Chasing partners two days before a deadline is a pain nothing else touches.

Assembly

Cover, cover letter, dot-leader table of contents, PDF bookmarks, tab dividers, page footers. One real package on record: 61 pages, 20MB.

What it refuses to do

On a document that binds your firm to the federal government, the guardrails are the product.

It won't invent a fact only you know

Availability percentages are never generated. Missing facts become visible placeholders, and a do-not-submit file blocks the package until a human resolves every one. On a real package that gate held back 62 blanks.

The AI can't write to your database

Extraction agents run read-only. Every write is hand-written, parameterised code. AI-drafted corrections pass a static validator, then a dry run, then a human approval. The chat editor's total write permission is two fields.

It won't reassign who did a project

A partner's uploaded project sheet that fuzzy-matches a project attributed to a different firm goes to review with zero writes. A partner's fee can never land in your own design-fee column.

Constraints

What you would be buying into

Every system has edges. Better you hear these from me on a webpage than discover them in month two.

A per-firm install, not cloud software

It runs on your machine. No user accounts or role permissions, and no multi-tenancy, because it was built for one firm inside its own building. That's good for data control, and wrong if you want a hosted product ten people log into.

Windows-first today

Document conversion, service management and default output paths assume Windows. Every entry point has a POSIX sibling, but a Mac or Linux shop is a scoped engineering item.

It produces the federal qualifications package

That covers any firm pursuing federal design work, and the analysis half transfers to construction management. It does not write general commercial RFP responses.

Output quality follows your record

It's built to say I don't know rather than guess. A thin database gives you a package with visible blanks. That's correct behaviour, and it's why the archive work isn't optional.

Heavy concurrent editing is unproven

There's real production hardening in there: resumable uploads, concurrency guards, per-conversation locks. But it's been run by one firm with one primary user, not a ten-person proposal team all editing at once.

No undo on the chat editor

The safety model is verify-before-assert, a two-field write allowlist, before/after display and a separate confirmation. It is not a version history. To reverse a team swap, you run the opposite swap.
